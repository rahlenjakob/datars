## Why agents do well here

- **Documents are TypeScript**, so the type checker catches most mistakes as the agent writes; recipes report unknown parameters with the nearest real one (*did you mean `labels`?*).
- **Every tool is deterministic.** The same document renders to the same pixels on every machine, so an agent's render is the reader's render, and a golden test holds in CI.
- **Every tool explains itself.** `check` and `lint` say what's wrong and how to fix it; `explain` traces any element back to its recipe, data row and expression values; `semantics` shows what a screen reader gets.
- **Small, readable recipes.** An agent that needs something the standard library doesn't do can [eject](/docs/custom-recipes/#eject-a-standard-recipe) a recipe of 30–150 lines and edit it, instead of hunting for the right combination of flags.

## The MCP server

`datars-mcp` exposes the toolchain over the Model Context Protocol (stdio, JSON-RPC 2.0). Build it from the repository, next to the CLI:

```sh
cd datars
cargo install --path crates/datars-cli     # the datars command
cargo install --path crates/datars-mcp     # the MCP server
```

Register it with your client. Most clients take a JSON entry like this:

```json
{
  "mcpServers": {
    "datars": { "command": "datars-mcp" }
  }
}
```

In Claude Code, from your project: `claude mcp add datars -- datars-mcp`.

> **Note** Documents are passed as paths. JSON documents work from anywhere; to compile `.ts` documents the server looks for the datars repository from its working directory, so run your client from inside the repository (or a project folder under it). Images are written under `out/mcp/` and their paths returned — and `render`, `film` and `replay` attach the image, so an agent can look at it directly.

## For agents without MCP

Everything the server does, the CLI does too, and every command takes `--json`:

```sh
datars check doc.ts --json           # diagnostics as JSON
datars lint doc.ts --json            # [{ rule, severity, message, fix }]
datars render doc.ts --state 1 --json --hash
datars describe std/bar --json       # a recipe's parameters, defaults, docs and tokens
datars describe --json               # all of them
datars profile doc.ts --json
```

Renders print the file they wrote; `--hash` prints the pixel hash, identical on every platform.

## What an agent should read

| Resource | What's in it |
|---|---|
| [`/llms.txt`](/llms.txt) | a compact index: how to write a document, the loop, every command, every recipe in one line — generated by `datars docs`, so it never goes stale |
| [Chart reference](/docs/std/) | every recipe's parameters, defaults, theme tokens and a real example (also `datars describe std/<name>`) |
| [`/schema/ir-1.json`](/schema/ir-1.json) | the JSON Schema of a compiled document — what a `doc.json` may contain (also `datars schema`) |
| `datars new <dir> --template chart\|story\|explorable\|map` | a working document to start from |

## A loop that checks its own work

1. **Profile the data** — `data_profile` (or `datars data profile data.csv`): column types, gaps, candidate keys, hints such as country codes that join to the atlas.
2. **Write the document** with standard recipes: a key on every source, colours as theme tokens (`$accent`), program states that set signals.
3. **Check** — `check`; fix every diagnostic.
4. **Look** — `render` each state, at a phone size too (`--size 360x640`); read the image.
5. **Watch the motion** — `film` each transition; the motion trails show where marks travel, and marks that cross-fade instead of moving point at a missing key.
6. **Lint** — `lint`; apply the fixes. `semantics` to read it as a screen reader would.
7. **Ask why** when something looks wrong — `explain` with the element's key.
8. **Test and publish** — `run_tests` for goldens, then `bundle` (or `datars publish`) and report the sizes.

```sh
datars data profile sales.csv
datars new sales --template chart
datars check sales/doc.ts && datars lint sales/doc.ts
datars render sales/doc.ts --state 0 --size 360x640 --dpr 2
datars film sales/doc.ts --from 0 --to 1
datars publish sales/doc.ts --alias sales --to site/
```

## Rules of thumb to give an agent

- Every data row has a key: `data.values(rows, { key: "id" })`. Identity carries marks through transitions.
- Colours are theme tokens (`"$accent"`, `"$categorical[3]"`), not literals — dark mode and brands then just work. A category's own colour is data: `keys: { S: { color: "#e8112d" } }`.
- Program states set signals; marks read them in expressions. Bare names are signals, `d.x` is the row.
- Prefer a standard recipe with parameters; eject one before writing from primitives.
- Look at renders and films before calling it done.
