datars is an engine for charts, maps and data stories that runs natively on the web, in iOS and Android apps, on the desktop, in video and in print. Write the chart once in TypeScript: every screen gets the same pixels, the same line breaks and the same motion — and you update it like an article, with no deploy and no app release.

Why it exists

Today, every screen gets its own copy of the chart

Web chart libraries don't run in native apps, app chart libraries don't run on the web, and neither makes your video or your print page. So a chart that matters is built again for every screen, by different people with different tools, and the copies drift apart. With datars it's one document, and every host plays it.

Why datars exists, and when to pick something else →

Every platform

One engine in every host, one line to embed

Not a web view, not a screenshot: the same Rust engine runs natively in each host — shaping the text, laying out, animating and drawing — so the chart in your app is the chart on your site, frame for frame. Every example produces identical pixel hashes on macOS, in wasm, on the iOS simulator and on Android.

  • Web

    <script type="module" src="/runtime/datars.js"></script>
<datars-view src="https://charts.example.com/c/worlds"></datars-view>

  • iOS & macOS — DatarsKit, SwiftUI

    DatarsChart(source: .url(URL(string: "https://charts.example.com/c/worlds")!),
            state: step)   // the story follows your SwiftUI state

  • Android — Kotlin view

    val chart = DatarsView(context)
chart.load("https://charts.example.com/c/worlds")

  • Video, PNG, SVG, PDF

    datars video worlds.ts --size 360x640 --dpr 3   # 1080×1920 MP4 + captions
datars render worlds.ts --out worlds.pdf         # vector PDF, searchable text

Stories that steer themselves

Scroll. The page tells the chart which step it's on; the engine flies the camera and morphs every country into its bar. No animation code — a story is a list of states, and every change between them animates by key.

Fly to Europe

The camera fits the countries with data. Setting a signal is all a step does: set: { focus: europe }.

The Nordics lead

Zoom again. Every frame of the flight is a pure function of the plan and the time — the same on a phone, in a video export, in a test.

Regions become bars

Each country's region morphs into its bar, because both are keyed by the ISO code. That is the whole trick.

{{alt:renewables}}
The document{{size:renewables}} incl. the world atlas 
export default doc({
  data: { world: data.atlas("countries"), renew: data.values(rows, { key: "id" }) },
  signals: { focus: signal.keyset(), shape: signal.str("map") },
  motion: motion({ select: { role: "region" }, matcher: "by-key" }),
  scene: group({ children: [
    view({ camera: { fit: { keys: "=focus" } }, when: e('shape == "map"'),
      children: [map({ source: "world", data: "renew", key: "id", value: "share" })] }),
    plot({ data: "nordic", x: "share", y: "name", children: [bar({ labels: true })] },
      { when: e('shape == "bars"') }),
  ] }),
  program: story({ steps: [
    step("world",   { set: { focus: [] } }),
    step("europe",  { set: { focus: europe } }),
    step("nordics", { set: { focus: nordics } }),
    step("ranked",  { set: { shape: "bars" } }),
  ] }),
});

Maps, no tile server

From the globe to a street corner, in one camera

Maps are part of the engine: countries are keyed shapes like bars, the basemap is a node in the scene, and the camera flies from space to a street in one move. Write data.tiles.auto() and the publish step cuts a basemap from OpenStreetMap and Natural Earth to exactly the places your story visits. No tile server, no API key, no per-view bill.

Big data, 60 fps

Four million stars. {{size:galaxy}} to start.

A synthetic barred spiral: every dot is one star of four million, and you can zoom from the whole galaxy down to a single one. The engine indexes the rows once into a pyramid of tiles; each frame draws only what the camera shows — a sample that keeps the galaxy's density from afar, every star up close. Camera tours run at 59–60 fps in Chrome.

Indexed once

The rows go into a quadtree whose levels are seeded samples of the data. Panning and zooming never re-read a row: tiles come and go, and a tile's stars are drawn from its cache.

Only what you see

The publish step ships the pyramid as an archive the page reads by byte range, from any static host. The first view needs a few hundred kilobytes; each zoom fetches the tiles it shows, and nothing else.

Sampled, never guessed

Every dot is a real row. A far-away view draws a uniform share of the stars — dense stays dense, sparse stays sparse — and the deeper levels fade in as you zoom until every one is there.

Batteries included

{{count:recipes}} charts, maps and guides, ready to use

Bars, lines, areas, scatters, pies and donuts, treemaps, waffles, funnels, waterfalls, sankeys, beeswarms, calendars, parliaments, choropleths, basemaps, point clouds, cards and sliders — the standard library covers the charts newsrooms and dashboards actually ship. Each is a recipe with typed parameters, sensible defaults and its own motion — and because every mark keeps its key, any of them can turn into any other.

  • Axes, legends and labels that fit. The engine measures text with the chart's own fonts; labels that would collide or be cut off at the edge are caught by datars lint.
  • Themed, not hard-coded. Every recipe draws with theme tokens, so your brand and dark mode apply to all of them.
  • Yours to change. datars eject std/treemap copies the recipe into your project as TypeScript.

Charts are content

Publish charts like articles, not like app releases

A chart is published as a manifest and immutable chunks — to any bucket, CDN or, like this site, GitHub Pages. Sites and apps install the runtime once; republishing a chart updates every embed without redeploying the site or shipping an app update. Each runtime picks the smallest variant it can play.

  1. T0SVG poster + accessible text. Shows before any script runs; works in email and RSS.
  2. T1Baked scenes per state, for playback-only runtimes.
  3. T2Recipes pre-expanded, data by hash. What this site plays.
  4. T3The source document, for runtimes with the recipe sandbox.
datars publish chart.ts --alias election --to site/
# site/c/election       ← the live manifest: embeds follow it
# site/chunks/b3_…      ← content-addressed, immutable, cached forever

Accessible

Every mark knows what it means

Semantics — role, label, value, reading order — are part of every mark, so the runtime can tell a screen reader what the chart says, not that there is a picture: “SD: 73”, not “rect”. On the web that's an ARIA mirror with live narration for story steps; in apps it's VoiceOver and TalkBack; engine-drawn sliders become native range controls.

  • Keyboard access to interactive marks, in reading order.
  • Reduced motion honoured on every platform: transitions become short crossfades.
  • A text alternative ships in every bundle — before any script runs — with an SVG poster.
  • Checked: datars lint flags interactive marks without a label, colliding labels and the theme's failed contrast checks.

Extendable

The globe at the top of this page is sixty-seven lines of TypeScript

No chart library ships a globe whose countries become planets. In datars it's one custom recipe — typed parameters and an expand function returning keyed shapes whose positions are expressions over each row — written with the same public API as the {{count:recipes}} standard recipes. Because every country keeps its key, coastlines morph into planets for free; the flights between layouts are motion rules.

motion: motion(
  { duration: 2.2, easing: "cubic-in-out", matcher: "by-path" },
  { when: { from: "globe", to: "orbits" }, select: { role: "datum" },
    route: route.spiral(0.35), choreo: choreo.ripple(0.55) },
  { when: { from: "orbits", to: "spiral" }, select: { role: "datum" },
    route: route.arc(0.3), choreo: choreo.stagger("value", 0.5) },
  { when: { from: "spiral", to: "blocks" }, select: { role: "datum" },
    choreo: choreo.wave(0.5, 0) },
),

Custom scenes get everything the built-in charts get: motion, themes, accessibility, every platform. Or start from a standard recipe: datars eject std/bar.

For developers and agents

Tools that answer “why does it look like that?”

Documents are TypeScript, so your editor type-checks them. datars dev opens a live page that morphs each edit in, previews phone widths and dark mode, and explains any mark you click. check reports what the engine couldn't do; lint catches colliding labels, low contrast and unstable keys; explain traces any element back to its recipe, data row and expression values; film draws a transition as a filmstrip; profile times every frame. The same tools are an MCP server, so a coding agent can build a chart and check its own work.

Get started

From a template to a published chart in four commands

1 Write a document

import { doc, data, group } from "@datars/sdk";
import { plot, bar } from "@datars/std";

export default doc({
  title: "Sales by region", size: [720, 420],
  data: { sales: data.values(
    { region: ["N", "S", "E", "W"], sales: [120, 98, 143, 87] },
    { key: "region" }) },
  scene: group({ children: [
    plot({ data: "sales", x: "region", y: "sales",
      children: [bar({ labels: true })] }),
  ] }),
});

2 Preview, lint, explain

datars new mychart --template story
datars dev mychart/doc.ts      # live page, morphs on save
datars lint mychart/doc.ts     # chart checks, with fixes

3 Publish anywhere static

datars publish mychart/doc.ts --alias sales --to site/
# site/c/sales + site/chunks/…  → any bucket, CDN or Pages

4 Embed

<script type="module" src="runtime/datars.js"></script>
<datars-view src="c/sales"></datars-view>
