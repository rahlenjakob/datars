No chart library runs on every screen

D3 draws in a browser. Swift Charts draws on Apple's platforms. Android has no charts built in, and a video or a printed page means redrawing it in After Effects or Illustrator. So a chart that has to be on your site, in your apps, in a video and in print gets built five times, by different people with different tools — and the copies drift apart.

datars is one that does. You write the chart once, as a small TypeScript document, and one engine plays it on the web, in native iOS and Android apps, on the desktop, in video and in print: the same pixels, line breaks and motion everywhere. You publish it like an article, so changing it takes no deploy and no app release.

Why a web library can't just add this

None of those rows is a feature bolted on. They follow from four decisions at the bottom of the engine about what a chart is and who draws it, which is why they're hard to add to a library afterwards.

The engine draws every pixel, text included

A deterministic Rust engine shapes text with the chart's own fonts, breaks lines, lays out, animates and rasterizes, compiled to WebAssembly for the web and to native code for iOS, Android and the desktop. Nothing is left to a browser or an OS, so every example hashes to identical pixels on macOS, in wasm, on the iOS simulator and on an Android emulator.

Every mark keeps its data's key

When the step, the filter, the data, the size or the theme changes, the engine matches marks by key and plans the motion. That's why there's no transition code: each bar knows which slice it becomes. Motion rules — routes, staggers, draw-on lines — are data you can override per pair of states.

A frame is a function of time

Transitions are planned once, then sampled. Scroll can scrub one exactly, a video is the same frames written to a file, an interactive session replays from its event log, and the test suite checks 64 frames of every transition against goldens.

A chart is content, not code

Sites and apps install the runtime once; charts arrive as small, content-addressed bundles from any static host, with an SVG poster and accessible text first. The document is data, so tools and coding agents can diff it, validate it against a schema, migrate it and repair it.

Should you pick it?

Pick datars when

  • the same chart has to be on the web and in your iOS or Android apps, or in a video or a PDF, and look the same in all of them;
  • your charts change — story steps, filters, live data — and readers should watch marks move, not jump;
  • editors should publish and fix charts like articles, without waiting for a deploy or an app release;
  • your story goes somewhere, from the whole world down to a street corner, with no tile server, API key or per-view bill;
  • you have a lot of data, hundreds of thousands to millions of points, and it has to stay smooth;
  • people who aren't visualization engineers, or coding agents, make the charts, and you want the tools to catch the mistakes.

Pick something else when

  • it's one browser-only piece, and your team wants to work in the DOM with a library it already knows;
  • you want to style marks with CSS or attach arbitrary DOM listeners to them;
  • it's a single small chart and page weight is everything;
  • you want a hosted editor and no code at all;
  • you need a large ecosystem of examples and answers today: datars is young.

What it costs you

The decisions that make it work everywhere have a price.

A bigger runtime, once
The web engine is {{runtime}} gzipped: a text shaper, a GPU renderer, a CPU reference renderer and the scene engine, compiled to wasm. It's cached across every chart on your site, and each chart after it is tens of kilobytes — but for one small chart on a light page, a small DOM library is lighter.
Canvas, not the DOM
The engine draws to a canvas, so marks can't be restyled with CSS or wired to arbitrary DOM listeners. Hovers, clicks, brushes and tooltips go through signals and intents; the page gets an accessibility mirror, and real links over the marks that link somewhere.
A new model to learn
You think in keyed marks, states and recipes rather than selections and timers. It's much less code for anything that changes, and when a morph looks wrong the answer is usually a key, which datars lint points at.
A young project
Fewer examples and answers online, APIs still settling, and not yet on npm or crates.io: you install from the repository. The document format is versioned with migrations, so documents survive changes. The status page lists what is verified and what isn't — Android has run on an emulator but not yet on a physical device, and desktop screen readers haven't been driven for real yet.
