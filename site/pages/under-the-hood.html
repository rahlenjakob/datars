Under the hood

How a chart gets from a TypeScript file to a frame

This page follows one small chart through every layer of datars: the document it compiles to, the bundle it is published as, the runtime that loads it, the engine that resolves and animates it, and the renderers that draw it. Along the way it explains why each piece works the way it does, what each frame is allowed to cost, and how the tests keep every platform drawing the same pixels. The figures quoted come from the source code or from benchmark data committed with this site, and each one says which.

The running example

Sweden's 2022 election results, as a story of four steps: bars, the same bars ranked, a pie and a donut. Each party keeps its identity from step to step, so its bar turns into its slice. The chart uses four standard-library recipes (plot, bar, pie and card), a derived table, a signal, a key table with names and colours, one motion rule and a program of steps. That is enough to touch almost every part of the system. Step through it; the rest of the page explains what happens when you do.

The shape of the system

datars is one Rust engine plus thin hosts around it. The engine never does IO and never reads a clock. Bytes and inputs go in; frames and requests for more bytes come out. It is the same engine at every stage. At publish time it runs in the CLI to bake scenes and draw posters. In the browser it is WebAssembly. In an app it sits behind a C ABI. Whatever the author's machine computed when publishing, a reader's device can compute again and get the same result.

A chart then travels through six stages, from the author's file to the reader's screen:

  1. doc.tsTypeScript using @datars/sdk and the standard library. Run once, at authoring time.
  2. The documentJSON: data, tables, signals, a keyed scene template, states and motion rules. No code.
  3. The bundleA small manifest plus content-addressed chunks, with variants from a static poster up to the full source.
  4. A runtime<datars-view> on the web, DatarsKit on iOS and macOS, datars-android, a desktop window, or the video exporter.
  5. The engineResolve a scene for the current state, plan the motion to the next one, evaluate the plan every frame, flatten it to a display list.
  6. A rendererwgpu on WebGPU, WebGL2, Metal, Vulkan or DX12; or the CPU reference rasterizer; or SVG and PDF.

Work happens in three places, and most design decisions come down to moving work from the last to the first two:

WhenWhat runsBudget
Publish timeRecipe expansion, fetching data, subsetting fonts, baking every state, drawing the poster, cutting map archivesWhatever it takes
Idle time on the deviceResolving the steps next to the one on screen, planning the transitions to them, tessellating their meshes, downloading their map tilesSlices of idle callbacks, while the reader reads

1 · The document

A chart starts as an ordinary TypeScript module whose default export is a call to doc(). The datars CLI compiles it with esbuild and runs it once in Node, and what the module returns is plain JSON. Inside a user's project the CLI uses that project's own @datars/sdk and @datars/std. Nothing from the TypeScript survives into the output: there are no closures left to call later. This is what the example looks like, trimmed:

export default doc({
  data: { votes: data.values({ party, share }, { key: "party" }) },
  keys: { S: { name: "Social Democrats", color: "#e8112d" }, /* … */ },
  tables: { ranked: { from: "votes", ops: [{ op: "sort", by: [["share", "desc"]] }] } },
  signals: { shape: signal.str("bars") },
  motion: motion({ select: { role: "datum" }, matcher: "by-key" }),
  scene: group({ key: "root", layout: { type: "stack" }, children: [
    plot({ data: "votes", x: "party", y: "share", color: "party", children: [bar({ labels: true })] },
         { key: "chart", when: e('shape == "bars"') }),
    pie({ data: "votes", value: "share", category: "party" }, { key: "chart", when: e('shape == "pie"') }),
    /* the ranked plot, the donut, a narration card */
  ] }),
  program: story({ steps: [step("bars", { set: { shape: "bars" } }), step("pie", { set: { shape: "pie" } }) /* … */] }),
});

Recipes are calls, not code

plot() and bar() don't draw anything. Each returns a node that names a recipe and its parameters. This is the plot as it appears in examples/votes/doc.json:

{ "kind": "use", "recipe": "@datars/std/plot",
  "params": { "data": "votes", "x": "party", "y": "share", "color": "party",
              "title": "Vote share by party, 2022 (%)",
              "children": [ { "kind": "use", "recipe": "@datars/std/bar", "params": { "labels": true } } ] },
  "key": "chart", "when": { "expr": "shape == \"bars\"" } }

The engine expands use nodes later, inside a sandbox (see resolving). That timing matters. A recipe can be expanded at publish time and shipped ready to draw. Or it can be expanded on the reader's device, against the standard library the runtime carries, pinned by content hash, so a runtime with a different library can't silently draw a different chart. An expansion produces templates: primitives such as shapes, texts, instances and groups, with expressions for their properties. It can also add derived tables.

Here is the example's scene at those stages: as the document holds it, expanded into primitives, and resolved for its first step. Rows that are the same node keep their place as the tree grows.

Expressions: a small, total language

Wherever a property depends on data or state, the document holds an expression: shape == "bars", or, inside the bar recipe, scale.x(d.party) and `${key.name(d.party)}: ${format(d.share, ",.1~f")}`. TypeScript lambdas compile to the same language. It is a typed JavaScript subset: d.x reads a column of the current row, a bare name is a column or a signal, and a.b(…) calls a host function (scales, formatting, key tables, measuring text). It is total. Division by zero follows IEEE rules, a missing column or signal is null, and NaN is the numeric null, so no data can make an expression throw.

Why a document

Because the chart is data, tools can work on it. datars diff compares two states or two versions. datars migrate upgrades it between IR versions. It validates against a JSON Schema. datars explain can say where any pixel came from, and a coding agent can write a chart and check it with the same tools. One more property matters for performance: the engine knows the whole chart before the first frame, so it can plan motion, prepare the next step and pre-build meshes without running anything the author wrote.

2 · Publishing

datars publish doc.ts --alias votes --to site/ loads the document into the same engine a reader will run, then works through it in order:

  1. Data. Every source the document names is fetched and handed to the engine, and ships as a data chunk. Tile archives are the exception. They are never bundled: the runtime reads the byte ranges its views need.
  2. Map tiles for every state are settled the way a host would settle them: resolve, answer the engine's range requests, repeat. Posters and baked scenes then show the basemap.
  3. Baking. Every state of the program is resolved to a complete scene.
  4. Expansion. Every use node is expanded through the sandbox, giving a document of primitives only.
  5. Fonts. The build works out which characters each face could ever be asked to draw. It gathers them from the document's text, the data bytes and the baked scenes. It adds month and weekday names only if dates are formatted, and both cases if the chart changes case. A face that draws only what the baked states show gets exactly those characters, plus the ten digits if its numbers tween. The body and number faces get the full set, as does every face of an interactive chart or of one whose text can arrive later (live data, host slots, streamed tiles). Subsets ship as chunks, and extra scripts' subsets load only when needed.
  6. Accessible text. For every state, the narration and the semantics tree (roles, labels, depth) go into one chunk. It becomes the chart's text alternative and its crawlable HTML.
  7. The poster: an SVG of the first state. Point clouds are drawn from a tenth of their sample for it, because every dot costs bytes. The SVG is tagged with the mode it was drawn in, taken from its background's luminance, so a runtime showing the chart in the other mode can skip it instead of flashing it.

Content addressing

Every chunk is named by the BLAKE3 hash of its bytes (b3:…), and the manifest lists which chunks each variant needs. Three things follow from that:

  • A chunk that several variants or charts share, such as a dataset shared by twenty charts, is stored and downloaded once. (Font subsets are cut per chart, so they are shared only between that chart's variants.)
  • A chunk never changes, so it can be cached forever.
  • Republishing writes only the chunks that are new, and writes the manifest last, by renaming it into place, so a reader never sees a manifest whose chunks aren't there yet.

This is what republishing the example looks like after one step's narration changed:

The manifest, c/<alias>, is the only file that changes. Fixing a typo in a published chart means publishing again; no page or app has to be redeployed.

Automatic basemaps

A map source declared as data.tiles.auto() gets an archive cut to fit the document's own cameras. The build asks the engine for every view the states settle on and every flight between them, the same way the engine evaluates them for a reader. It then fills a PMTiles archive with standard basemap layers from OpenStreetMap and Natural Earth, fetched once into a local cache. Write a story about Rio, and the build fetches Rio. The archive sits next to the document with a job file acting as its lockfile: while the cameras don't change, the archive is current and is reused byte for byte, offline. Publishing ships it under a content-hashed name. It is still not part of the bundle: readers fetch it by range.

3 · The web runtime

On a page the chart is <datars-view src="…/c/votes">. It is a custom element with a shadow root holding the canvas, the poster, a text layer, an accessible mirror of the chart (a list plus a live region), the narration card and link overlays. Everything that decides pixels runs in the WebAssembly engine. The element's job is to feed it bytes, time and input, and to put what comes back on screen.

Starting a chart

  1. The manifest, a few kilobytes, arrives first.
  2. An engine build is chosen from three, and each loads at most once per page, shared by every chart on it. full includes the QuickJS sandbox and is used only when every variant needs it (T3, or raw source documents). Otherwise the runtime uses core where the browser has a WebGPU adapter, and core-gl, which adds the WebGL2 backend, where it doesn't. The check for an adapter happens once, as the runtime loads, alongside the first manifest. It checks for a real adapter, not just navigator.gpu: some browsers have the API and no adapter.
  3. The poster downloads at the same time, unless it's over 200 KB. It appears only if the engine hasn't drawn within 600 ms, and never when an engine is already running on the page (the chart will be ready quickly). It is also skipped if it was drawn in the other light/dark mode, since a light poster flashing before a dark chart looks worse than a moment of empty space.
  4. Chunks. The engine opens the manifest, picks the best variant it can play and asks for that variant's chunks. They download in parallel. If two charts ask for the same chunk at the same moment (the same fonts, say), it downloads once.
  5. Heavy steps wait for a quiet page. Opening the document and attaching the GPU surface are the costly parts of a start. They wait until scrolling has paused (180 ms since the last scroll event) and no other chart is mid-transition. GPU surfaces attach one at a time.
  6. The first frame is drawn and the canvas fades in over the poster (0.22 s).

So what a reader sees while a chart starts depends on how quickly its engine draws:

Nothing on the page moves at any point. The page reserves the chart's box before any script runs, from the document's aspect ratio, a minimum height and a phone ratio written into CSS variables. @datars/react sizes its box the same way on first render, before the chart has loaded. The site mounts a chart when its slot comes within 700 px of the screen. Off screen a chart draws nothing, and its clock, levels and tiles resume when it's back. Far away, the React component releases its engine altogether.

The frame loop

Frames run only while something moves. When nothing does, the engine returns a wake_at time (an autoplay hold ending, a live refresh due) and the element sleeps until then. Each frame the element passes the time to View.frame(now). The engine evaluates, fills and flattens, the renderer draws, and the element learns whether anything is still moving. If one chart is mid-transition, other charts that are only busy (a clock ticking, tiles arriving) draw every third frame, so the one being read keeps its frame rate.

Idle time, the most important time

While the reader looks at a step, the element runs View.prepare() in idle callbacks, a slice at a time:

  1. It resolves the steps before and after the current one, and plans the transitions to them. A step then starts from a finished plan and has nothing to compute on input.
  2. It hands each prepared target's display list to the renderer to warm: every mesh the landing frame will draw is tessellated and uploaded in advance. If a target's map tiles are still downloading, it warms again when more bytes arrive, so the landing frame doesn't tessellate what arrived late.
  3. It downloads the map tiles those steps will need, along their flights and around the view, behind anything visible now.

The result is on the performance page: in the committed runs, the median stall from a click to the first moving frame is a few milliseconds.

Adapting to the device

The engine's per-frame budgets are sized for a desktop, and a phone's CPU takes three or four times as long for the same work. So the page gives the engines a share of their per-frame budgets, and times the main-thread cost of every frame that moves. The share starts at a half and never goes above three quarters, since WebAssembly runs the same work two to three times slower than native code. A frame over 14 ms cuts it to 70% at once; while the running average is above about 8 ms it drops by a tenth a frame, down to a fifth. When frames are cheap again (the average under 4 ms), it grows back. On a slow device, detail then arrives over more frames instead of frames being dropped. The share is one per page, because it is the device that is slow, not a particular chart. The engine treats it like any other input (see determinism).

Text you can select, and a chart you can hear

The canvas is pixels, but the chart's words are real text as well. The engine reports where every line of every text is drawn, with its box, baseline, direction and font face. The text layer lays one transparent span per line exactly there, in the chart's own font (the engine hands over the face's bytes, and each face is registered once per page), stretched to the drawn width. The selection highlight then sits on the drawn glyphs, and copy, find-in-page and crawlers all see the words.

That layer is aria-hidden. Screen readers get the mirror instead: the engine's semantics tree as a list of labelled items in reading order ("Social Democrats: 30.3"), the chart's controls as native range inputs, and each step's narration in a live region. Otherwise every title and label would be read twice. Keyboard: → or space for the next step, ← for the previous, Escape to go back. Shift+D, or ?datars-perf in the URL, opens a panel with every frame's cost.

4 · Resolving a scene

A resolve turns the document and the current signal values into a scene: a keyed tree of groups, views (a clipped viewport with a camera), shapes, texts, images and instance sets. The engine walks the scene template with a context: the layout box it's in, the scales in scope and the current datum. Along the way it evaluates properties, expands recipes, lays out boxes and shapes text.

Tables

Sources become typed, columnar, keyed tables. The example's votes table is keyed by party. Derived tables are pipelines of operations over another table: filter, derive, aggregate, sort, top, bin, window, join, pivot, unpivot, union, sample and interpolate, plus layout algorithms: treemaps, packs, waffles, parliaments, beeswarms, Sankey links and more. A table that doesn't depend on the layout box or scales is computed once and kept across resolves until its data changes. One that does is cached per box and scope. The example's ranked table is computed once, however often the reader steps back and forth.

The expression VM

Expressions are parsed and type-checked when the document loads, then compiled to register bytecode. They run over rows in chunks of 1,024. Each instruction runs over a whole chunk before the next begins, so an expression over a hundred thousand rows costs about a hundred dispatches per instruction, not a hundred thousand. Registers hold typed lanes (numbers, booleans, values), and columns are borrowed, never copied. Fast kernels cover arithmetic, comparisons, maths and selects. Everything else falls back to a scalar interpreter that defines the semantics, so results are the same either way. Output NaNs are canonicalized, because hardware differs in the NaN bits it produces.

Recipes in a sandbox

Unless the bundle was expanded at publish time, use nodes expand here, in QuickJS. The sandbox has no ambient authority: no Date, no Math.random, no IO, no timers. Math's transcendental functions are replaced with the engine's deterministic ones, and every call runs under a time budget and a memory limit. Expansions are cached by recipe, parameters and context. The same QuickJS is compiled into the web runtime's WebAssembly and into native builds, so a recipe expands identically everywhere.

Layout, scales and keys

Layout is engine-level because it depends on measured text: an axis is as wide as its widest label, so a recipe can't guess the margins. A container lays its children out in rows or columns, stacks them, or places them in a grid. A child's size is a fixed length, a percentage, auto (measured) or fill with a weight. Scales resolve within their layout box, so scale.x(d.party) is a pixel position in the plot's box.

Every mark gets a key, usually from its data row. Keys chain into key paths from the root. A key part is a number, a string, or the i-th unit of its parent datum (one seat of a party, one cell of a waffle). Key paths are how the engine identifies an element across resolves, how motion pairs elements, and how tools address them. Placement passes, semantics and caching

After the tree is built, a few passes place what depends on everything else. Cards move to avoid data marks, labels are decluttered, and text is kept inside its frame. Every node can also carry semantics (a role, a label, a value, an action). That is what the mirror, the text alternative and the accessible-text chunk are made from.

A resolved scene is cached under a signature: the program's position, the viewport size and every signal's value, up to 256 scenes. Going back to a step never resolves it again.

Flattening

The scene is flattened into a display list. This is a flat sequence of drawing operations in paint order: fill, stroke, glyphs, instances, image, and push or pop for clips and layers. Each carries its accumulated transform, opacity and clip. Colours in the scene are inks such as $ink-2 or $palette[3], and they are resolved against the theme only here, as late as possible. Switching between light and dark or changing brand tokens flattens again, but never re-resolves. Coordinates are CSS pixels; each renderer multiplies by the device pixel ratio.

5 · Motion

When the state changes, the engine resolves the new scene and plans a transition from what's on screen to it. The planning is the expensive part and happens once: at the change, or earlier in idle time. Every frame after that is plan.at(t), a cheap pure function of normalized time that returns a scene. at(0) is exactly the old scene and at(1) exactly the new one, bit for bit. So the settled state after a transition is identical to resolving that state directly, and anything that can supply t can drive the plan: a scroll position can scrub it, a video exporter can render any t, and a second change mid-flight re-plans from at(t). For the example, the performance page measures planning bars → pie at 0.2 ms and one frame of it at 0.025 ms (datars profile, CPU reference).

Elements and rules

Both scenes are flattened into elements: every shape, text and image, and every instance of an instance set. Each records its transform into the root's space, its opacity, its bounds and its structural parent. Groups and views are structure.

Which element moves how comes from motion rules, which cascade like CSS. A rule applies when its selector (a role, a node kind, a key-path prefix) matches the element and its state globs match the transition's from/to states. Rules are ordered by specificity and then by source order, and for every field the last applicable rule that sets it wins. Unset fields default to 0.9 s, cubic in-out, no delay, matching by key path, all together, straight routes, disc morphs, fading in and out. Recipes can contribute defaults of their own, such as a line drawing on, scoped to where they're used. The example adds one rule: data marks match by key.

Matching: who becomes whom

By default elements pair by key path, and in the example the paths differ. The Social Democrats' bar lives at …/("body",)/("center",)/("area",)/("marks",)/("S",) inside the plot recipe, and their slice at ("chart",)/("S",) inside the pie. The key ("S",) is the same, though, and keys are identity across recipes: a data mark that no path matches pairs by its own key, when that key names one data mark on each side. The example's one rule says the same explicitly. Matchers, from most common to least:

  • By path (the default): the same element in two versions of the same chart.
  • By key: the same datum across different recipes, such as a bar becoming a slice or a country lifting off a map into its bar.
  • Hierarchy: a parent key on one side splits into its unit keys on the other, the parent's geometry partitioned into pieces. A party's bar breaks into its seats, and merges back. Data marks left unpaired do this without a rule, too.
  • Nearest: for unkeyed sets, a deterministic optimal assignment by position (an auction for up to 2,000 elements per side, greedy nearest beyond).

Anything unmatched enters or exits through a ghost, a partial state relative to its real one. It can fade, scale about an origin (bars grow from their axis), shift, grow from its parent datum's centre, or draw on along its length.

Tracks: how a pair interpolates

Every matched pair becomes a track, and a shape's track picks a plan for its geometry by trying these in order:

{{code:crates/datars-motion/src/plan.rs#L499-513}}
  • Same: nothing to do.
  • Shift: every point of the path moved by one vector, as when a map is fitted into a box a few pixels taller. Interpolating point by point would be exactly a translation. So the outline is kept, and a transform moves with the easing: the same frames, but geometry that never changes, and meshes the renderer can keep. On a map of 3,100 counties, that is the difference between re-tessellating every county every frame and not at all.
  • Extend: one open line runs on from the other (a series with a new data point). The longer line is drawn, trimmed from the shorter one's length to its own, so it grows along itself instead of bending into shape.
  • Param: the same kind of geometry, so its parameters interpolate. Rectangles lerp x, y, width and height (bars to ranked bars); arcs lerp angles and radii.
  • Points: lines keep their vertices. A line's vertices are data points, and other marks may sit on them, such as the dots of a line chart. Resampling both lines by arc length would pull every vertex off its point. Instead the two lines are merged: every vertex of both is kept and given a partner on the other line at the same relative place. The place is found by x when both run left to right (points travel straight up and down), otherwise by arc length, anchored at the ends and at the vertices a riding marker shares. A point with no partner grows out of the line.
  • Morph: everything else. Both shapes become closed rings, resampled to the same number of points (32 to 256, by on-screen size), wound clockwise and started at the point straight above their centre, so vertex i of each are neighbours. The default disc strategy moves the centre in a straight line while the outline passes through a disc of matched area mid-flight (roundness 0.85·sin πt). A bar rounds into a blob, flies, and unfolds into its slice. Going convex to disc to convex, a shape can never fold over itself. The resample strategy lerps the aligned outlines point by point instead.

Paints interpolate in OKLab, so colours pass through perceptually even midpoints rather than muddy ones. A number reshapes every frame as its value tweens. Two different texts crossfade, and never at the same time: the old one fades out in the first half and the new one in during the second, because two overlapping sets of words can't be read. An element moving between containers flies in the root's space, in a flight layer that matching ignores, so it keeps its logical path and a re-plan mid-flight continues it instead of starting over.

Instance sets, such as a million points, don't become a million tracks. A column track interpolates their columns (x, y, size, width, height, opacity, fill) as flat arrays, each instance with its own time window. Entering and exiting instances ride along in the same node, from and to their ghosts. Past 100,000 instances a set isn't planned one by one: it crossfades as a whole, unless the target is the same set moved by one vector (a dot map fitted to a slightly different box), in which case the one set moves under a transform, as a shifted outline does.

Timing, paths and easing

Choreography gives every element a window [start, end] within the plan's time. The options: everyone together, staggered in an order over a share of the window, phased (exits, then updates, then enters), or a wave or ripple delayed by position. Routes are offsets added to the straight path, such as an arc, an elbow (x first, then y) or a swirl. Every route's offset is exactly zero at both ends, so no detour can leave a settled state off by a hair. Easings: linear, named families in and out, CSS cubic-bezier, steps, keyframes, and springs. A spring is a damped oscillator evaluated in closed form and normalized to end exactly at 1; re-planned mid-flight, it carries its velocity over instead of stopping dead. Cameras are a centre and a log scale, so zoom interpolates the way people perceive it. Long moves follow the van Wijk–Nuij path (zoom out, pan, zoom in), which makes a world-to-street flight read as one continuous move.

6 · Maps and big data

A geo coordinate system on a group fits a projection to the group's layout box. Cameras fit to a lon/lat box, or to a list signal a story step sets. Map data at every zoom is too much to resolve into a scene, so a tiles node resolves to an empty placeholder plus a binding. The binding is filled every frame, settled or mid-flight, from the camera that frame has.

Which tiles, and how they arrive

From the transform that takes projected content to the screen (camera included) and the rectangle the view clips to, the engine computes which tiles are visible, and at what zoom they would appear 512 px across. For Web Mercator that is exact. For other projections it uses the local scale at the view's centre, so an Equal Earth world map and a SWEREF city map both ask for sensibly detailed tiles.

As the camera moves, squares change level without popping. Zooming in, finer data fades in over 0.3 s above the coarser data drawn there before; zooming out, the coarser squares draw at once and the finer ones fade out on top of them, so nothing shows through:

Archives are single PMTiles files: a header, directories, and tiles. Because the engine does no IO, a missing tile becomes a range request (source, offset, length). The host fetches it with an HTTP Range header, any static host or CDN answers, and the bytes go back through provide_range. There is no tile server and nothing per view to pay for.

Budgets, so a flight never freezes

A flight arriving at street level wants dozens of new tiles at once, and each costs time to decode and style. A frame that did it all would freeze. So each frame has budgets, and whatever isn't ready yet is drawn from something close enough:

{{code:crates/datars-engine/src/tiles/mod.rs#L207-221}}
  • Decoding: 64 KB of decompressed tile bytes per frame, beyond the first tile, which always gets through. A tile too big for a frame's budget mid-flight waits for the landing: from 85% of the way through, big tiles decode one per frame as the camera slows. Bytes that arrive but can't be decoded yet are kept (up to 512 tiles' worth), so nothing is downloaded twice.
  • Styling: 8,000 features per frame, again with at least one tile always getting through. Styling runs each feature through its layer's template, at roughly half a microsecond a feature, and a street tile holds thousands. A tile already styled at a nearby zoom keeps that styling a frame or two longer.
  • Stand-ins: a square whose tile isn't ready is drawn from its nearest ancestor that is, up to eight levels up, overzoomed and clipped to the square. The view is always covered, and detail sharpens into place.

Labels

Place names are placed by priority without overlapping, and they give way to every authored text on the canvas: titles, legends, callouts, data labels, the attribution. During a flight, placement changes as tiles and zooms change, and a label that simply appeared or vanished would flicker. So each flight frame also looks six samples back over the last 0.3 s. A label's opacity is the share of those samples in which it was placed, so labels fade rather than pop.

Point pyramids: millions of rows, a frame's worth at a time

An instances node with lod draws a table of any size. Its rows are indexed once into a quadtree of tiles, or read by range from a point archive. Each row gets a priority, a hash of its index. Level ℓ holds the fraction budget · 4ℓ / n of all rows, and a row belongs to the shallowest level whose fraction its priority falls under. The rows down to any level are therefore a uniform random sample of the data: dense regions stay dense, sparse ones sparse, and no seam shows where tiles meet, because the fraction is the same everywhere. A tile that fills up, in a region far denser than average, passes the rest of its rows to its children. Tiles stay bounded, and dense regions simply get deeper levels.

Which levels a frame draws depends on how many of their rows are in view. Levels join coarse to fine while the rows drawn so far, times the next level's growth, still fit the frame's budget (150,000 rows by default). A view of everything stops early; zoomed in, it goes on down to every row:

A frame draws only the tiles its camera shows: at most 256 per level, none smaller than 96 px on screen. Each tile's instances are built once, by running its rows through the node's template, and then reused, so panning re-resolves nothing. Building is budgeted too, at 4,000 rows per frame times the device's work share, and new detail fades in over 0.35 s instead of appearing. That is how the four-million-star galaxy on the front page draws its stars from a {{size:galaxy}} bundle: its stars are generated from a seed, and a view only ever builds the few levels it shows.

7 · Rendering

A display list is backend-neutral. The GPU backend is one renderer for every platform, built on wgpu: WebGPU in the browser with a WebGL2 fallback, Metal, Vulkan or DX12 natively, and an offscreen target with readback for tests and image export.

Meshes are made once and kept

Every path is tessellated into triangles by lyon once, in its own local coordinates, and cached by content hash. A frame is then mostly uniform writes, instance uploads and draw calls. Moving, scaling or recolouring a mark changes a uniform, not its mesh. The cache key decides when a mesh can be reused:

MeshKeyed bySo
FillPath hash, fill rule, tolerance bucket (one per octave of scale)A path with only straight edges (buildings, water, counties) has one key at every zoom: a camera flight doesn't re-tessellate the city. Curves get finer as they grow.
StrokePath hash, width bucket (a quarter octave), cap, join, miter limit, dash, toleranceThe shader extrudes to the exact width, so a width bucket only shapes the joins. Under a non-uniform scale the mesh is built in device space instead, to keep the stroke even.
GlyphFont, glyph, size bucket (an eighth octave), toleranceText at every size shares outlines; a halo is a round-joined stroke under the fill.

Vertices are stored relative to their path's centre, and the translation back is composed with the draw's transform in double precision on the CPU. So a street far from the map's origin, under a huge zoom, still lands within single-precision accuracy on screen.

Per-frame budgets and stand-ins

A mesh drawn for the first time goes into a per-frame arena, one buffer for everything new. Drawn again the next frame, it is retained: its vertices and indices are appended to shared GPU pages of 1 MB, and each page is uploaded in one write a frame. Creating or destroying a buffer is a trip through the driver on OpenGL and to the GPU process on WebGPU, so retained meshes share pages rather than getting buffers of their own. At most 64 meshes are retained per frame (times the device's work share, at least 16), but meshes of 16 KB or more are retained at once rather than copied through the arena again. A morph's outlines are new every frame and never touch the cache: thousands of entries per frame would be the hitch, and would evict the city.

A frame tessellates 24 meshes (times the device's work share) before it starts looking for stand-ins: a mesh already built for a neighbouring width or tolerance bucket, drawn instead of building the exact one this frame. Zooming crosses a stroke-width bucket every quarter octave, and without stand-ins each crossing would re-tessellate every road on screen in one frame. For thin strokes on straight edges (up to 2.5 device px: borders, grid lines) the stand-in is the path's last mesh at any width, and while the host says the frame is moving it is used at once, without spending the budget on a width that will be stale a frame later. Exact meshes are built when things settle, and in idle warming, so still frames are always exact.

Text is outlines, tessellated like any path, and each glyph's mesh is cached per font, size bucket and tolerance. A run of text drawn two frames running is joined into one mesh for its fill and one for its halo, as the CPU reference fills a run as one path. Every draw call costs on OpenGL (older phones, the Android emulator, WebGL), and a map's place names had been most of its draws: a flight over Sweden went from 730 draws a frame to 118. Text new every frame, such as numbers counting up, stays glyph by glyph, drawn from the glyph cache. At most 24 runs are joined per frame (times the device's work share), and text never waits for a stand-in, so labels don't blink.

Instances, clips, layers, colour

An instance set is one instanced draw. Symbols are analytic signed-distance shapes (the polygon comes from the same symbol geometry the CPU reference fills), and rectangles are per-axis box SDFs, each with its own colour, opacity, size and optional outline. A million points are a million quads with exact anti-aliased edges, not a million meshes. A set of 32 or more that doesn't change from frame to frame, as when the camera moves over a dot map, is flattened once (its inks resolved, its columns converted) and, from its second frame, drawn from instances kept in GPU pages of their own: not rebuilt and uploaded again every frame. Fading doesn't count as a change: the opacity of the groups around a set is a per-draw alpha, not baked into its columns, so a tile easing in or a level crossfading draws from the same buffer. A frame keeps at most 48 new sets (times the device's work share), so a whole level of cells arriving at once spreads over a few frames. Clips count in the stencil buffer: a clip increments the samples it covers inside the current clip, content draws where the count equals the clip depth, and popping decrements it. A translucent stroke blends each sample once, also through the stencil, so it doesn't darken where lyon's triangles overlap at joins. Layers render offscreen and composite with opacity and Normal, Multiply or Screen blending. Paths and glyphs get 4× MSAA. Colours are straight sRGB and the target is a non-sRGB format, so blending happens in the same space as in the CPU reference.

Choosing a backend in the browser

The renderer asks for a WebGPU adapter and device before touching the canvas. A WebGPU surface claims its canvas for good, and a browser that offers WebGPU without an adapter would otherwise leave nothing for the fallbacks, and no chart. If there's no adapter, the core-gl engine tries WebGL2 (every Safari since iOS 15 has it). If that fails too, the CPU reference draws into a 2D canvas.

The CPU reference

One renderer is written to be identical everywhere rather than fast. Geometry is flattened at 0.1 device px and stroked in double precision using only basic IEEE operations (+, −, ×, ÷, √, rounding) plus the engine's own maths for round joins and caps. Rust never fuses or reorders float operations, so this is bit-identical on every CPU. Coverage is computed in 24.8 fixed point with integer accumulation, which gives exact-area anti-aliasing. Compositing is integer arithmetic on premultiplied RGBA8, with one correctly rounded division by 255 per result. It's single-threaded, with no hash maps, no time and no IO. The bytes it produces are the same on x86-64, arm64 and WebAssembly, which makes it the anchor of every test. It renders goldens, server-side images and the fallback, and, for now, the iOS and Android views. SVG and PDF backends draw the same display list as vectors.

8 · Determinism

The first principle is that the same document and the same inputs give the same pixels on every target. It's what lets a chart be authored on a Mac, tested on Linux CI and shown on an Android phone with confidence that all three agree. Keeping it takes discipline in a few specific places:

  • Maths. Platform maths libraries differ in their last bits. The engine's crates are forbidden by lint (clippy.toml) from calling sin, cos, exp, ln, powf, atan2, hypot and the rest, and must use datars_math::m, a wrapper over a pure-Rust libm that gives the same bits natively and in WebAssembly. sqrt, floor, ceil, round and abs are exact IEEE operations and allowed. Fused multiply-add is banned, because targets differ in it.
  • Collections. HashMap and HashSet are forbidden in engine crates, because their iteration order is random. Ordered maps are used instead.
  • Randomness. Only a seeded generator. The dot-density layout, the point pyramid's priorities and the galaxy are all functions of their seeds.
  • Time is an input. The engine is handed the time of each frame and never reads a clock. That is also why its budgets are counts (bytes, features, rows, meshes) and not milliseconds. A millisecond budget would make the frame's content depend on how fast the machine happened to be. Adapting to slow devices is therefore explicit: the host measures and hands the engine a work share, and that share is an input like any other.
  • IO doesn't exist inside the engine. It emits requests (a source, a data slot, an atlas, a byte range) and receives bytes. Timing of the network can change when something is drawn, never what.
  • Recipes run in a sandbox without clocks, randomness or IO, with the same deterministic maths.

9 · Testing

Goldens: the cross-target oracle

datars test runs every example document. For each state it records a hash of the scene and a hash of the CPU reference's pixels. Each transition is sampled 64 times and the samples are hashed together. Over the samples it checks the motion invariants: at(0) is the old scene and at(1) the new one, bit for bit; no NaN appears anywhere; entering elements never fade back out and exiting ones never come back (a flash); an element on both sides never dips in opacity and recovers (a blink); and nothing visible jumps more than about a third of the view's diagonal between two samples (a pop). That morphing outlines never turn inside out is property-tested in the motion crate itself.

The goldens are hashes and text, kilobytes in git. Images are made only for failures and review, as filmstrips and motion trails. This is the example's golden file:

Because the engine is deterministic, every other target checks itself against the same hashes. The web tests run the WebAssembly runtime over every example that needs no external files (the native tests cover the rest) and require the same pixels. The C ABI golden test runs on an Android emulator. The Swift package has its own tests. A difference anywhere is a real change, never noise. That is also why a golden is accepted only after looking at the renders, with every other test passing: a wrong golden would hide the same regression on every platform at once.

GPU against the reference

The GPU renderer can't be bit-identical to the CPU reference: rasterizers differ in how they cover edge pixels. datars gpu draws every example state both ways and compares them in ΔE (perceptual colour difference). The limits are a mean ΔE of at most 1, at most 0.5% of pixels visibly different, and at most eight pixels inside regions that differ, where a region is a 3×3 block of visibly different pixels: anything 3 px thick that one renderer drew and the other didn't. All 56 example states pass. The closest are the globe's rim, where whole islands are thinner than a pixel and a sub-pixel border's coverage rounds differently under 4×MSAA than under exact coverage, and the pixels where many such borders cross.

Performance, measured frame by frame

  • datars profile doc.ts resolves every state cold and warm. It then steps every transition at 60 fps on a headless GPU and reports, per transition: the stall, per-frame engine and GPU time, meshes tessellated by kind, map tiles decoded and styled, instances rebuilt and uploaded, and the worst frames with what they did. --timeline prints every frame. Times are this machine's, but the counts aren't: a transition that rebuilds 20,000 or more instances every frame is flagged even when a desktop draws it in 3 ms, because a phone won't.
  • scripts/perf-browser.mjs does the same in real Google Chrome, with its GPU stack, WebGPU and devicePixelRatio 2. It steps every transition of every chart on a site and records frame rate, lowest frame rate, dropped frames, stalls and time per frame. It can also scroll pages and record layout shift and long tasks (attributed to each chart's start-up phases), and throttle the network and the CPU to phone speeds. With --profile it records a CPU profile of each transition (wasm included, 0.1 ms samples) and names the functions behind its busiest 50 ms, which catches a one-frame spike that a frame-time readout can only point at. The shipped engines carry no function names, so NAMES=1 scripts/build-wasm.sh builds a named copy of the same code for it to load instead. That is how a 50 ms frame in a morphing map came down to one cache freeing thousands of per-frame outlines at once. The performance page is built from its committed runs.
  • datars budgets checks every bundle's and runtime's gzipped size against committed budgets.

The C ABI is small on purpose. It creates a view, loads a document or opens a manifest and provides its chunks, and answers the engine's data and range requests. 11 · Delivery

A published chart is two kinds of file: c/<alias>, the live manifest, and chunks/<hash>, immutable content. Any static host serves that layout, GitHub Pages included, under any subpath. This site's charts are published exactly that way. datars serve is a small server for the same layout plus the runtime, and it behaves the way a CDN would:

  • It answers HTTP Range requests: tile and point archives are tens of megabytes, and a view asks for a few kilobytes of them at a time.
  • It gzips whole responses for clients that accept it: text, WebAssembly, JSON, fonts and chunks, but not formats that are already compressed (PNG, JPEG, MP4, WOFF2, PMTiles), and not ranges. Each file is compressed once and the result kept. The engine's WebAssembly goes out at about a third of its size.
  • Content-addressed paths are cached as immutable: chunks wherever the site puts its delivery folder, and hashed runtime folders. Manifests are no-cache, because republishing rewrites them.

Which variant a reader gets is decided on their device, from the manifest alone: the runtime takes the first variant, richest first, whose needs it meets. The same published chart therefore plays differently on different runtimes, and never fails to show something:

The runtime folder that @datars/vite writes is named after a hash of the engines' contents. A rebuilt engine therefore always gets a new name, and a returning reader's cache can never pair old WebAssembly with new glue code. The runtime is {{runtime}} gzipped, loaded only on pages with charts, and shared by every chart on the page. Each chart after that is its own bundle; the example is {{size:votes}}.
