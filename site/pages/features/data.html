Data from anywhere

Your rows, wherever they live

A chart can carry its rows, fetch them when it opens, refresh them live, take them from the app that shows it, or make them on the device. Whichever way they arrive, they become one kind of table — typed, keyed — and keyed rows animate into place. The engine never fetches anything itself: the page or the app does, so your API, your sign-in and your privacy rules apply unchanged. Try it with rows of your own:

The chart’s own sample: the Nordic capitals.

Rows

Edit a number and its bar moves; add a line and a bar grows in. Paste your own CSV or JSON, or drop a file here — it stays in this page.

What the page sends

view.provideData("rows", csv);

The page reads only the header line, to offer its columns and rename the two you pick to the slot’s label and value. The rows go to the engine as they are: it splits them, reads ; and tab delimiters, decimal commas and NA or .. as missing, checks them against the slot, and keys them by label.

Live, answered by your code

A live source, and an API that misbehaves on purpose

This chart’s document asks for feeds/orders.json every 1.5 seconds. Each request goes past the page first as a datarequest event, and here the page answers it from a simulated API — make it slow, make it fail, open a new region — and watches what the chart does.

    view.addEventListener("datarequest", (e) => { … });

    A failed request costs nothing

    A rejected answer leaves the chart on its last good rows; the runtime logs a warning and asks again on schedule. Readers see stale numbers, never an empty chart.

    Slow answers don’t pile up

    A refresh is asked for only when the last one has come back: with a latency longer than the interval, the chart simply refreshes less often. Watch the log’s gaps.

    Keys make it readable

    Rows are matched by region: bars slide to their new ranks, a new region grows in, a closed one shrinks away, and the total counts to its new value.

    Simulated orders, not real traffic. Published without this page’s handler, the element fetches the URL itself — your API, with its CORS and headers; datars serve replays a folder of numbered snapshots as a feed (live sources). Figure source.

    Derived tables · keyed

    Reshape in the document, and the chart follows

    Each step is a derived table — filter, aggregate, top-n, a window — and each state shows one. The cities are keyed by (country, city) and the summed rows by country, so when cities are added up the engine knows which bar is whose parent: they gather into it.

    tables: {
  filtered: table("cities", op.filter(e("d.pop >= 15"))),
  summed:   table("filtered", op.aggregate(["country"], { pop: ["sum", "pop"] })),
  ranked:   table("summed", op.top(6, "pop"), op.sort(["pop", "desc"])),
  shares:   table("ranked", op.window("share_of_total", "pop", "share")),
}

    From the app

    One chart for every user, their rows on their device

    This spending chart was published once, with a sample. A banking app ships it — or downloads it — and hands in the signed-in user’s rows. They never leave the phone, no chart is built per user, and a redesigned chart reaches every user without an app release. Switch account and the same chart morphs to the other rows, keyed by month and category.

    // Web
view.provideData("spending", rows);
// SwiftUI
DatarsChart(source: .url(chartURL),
            data: ["spending": rowsJSON])
// Android
view.provideData("spending", rowsJSON)

    Rows without the key or the columns the sample has are refused with the reason, and the chart keeps what it showed — try “Broken rows”. Data slots in the docs.

    Where rows come from

    Eight ways in, one kind of table

    Every source becomes the same thing: a typed, keyed table the scene reads. Change where the rows come from and nothing else in the chart changes.

    In the bundle

    Rows written in the document, or files beside it — CSV, JSON, GeoJSON. Publishing copies them into the bundle as content-addressed chunks, shared by hash between charts, and draws the poster and the accessible text from them.

    data.values({ party: ["S", "M"], share: [30.3, 19.1] }, { key: "party" })
data.url("sales.csv", { key: "month" })   // a file next to doc.ts

    Arrives with the chart · votes

    Built-in atlases

    Every country’s outline, by ISO code, shipped as a compact topology the charts on a page share. Join your table to it by code.

    data.atlas("countries")

    Arrives once per page, cached · maps

    Fetched when it opens

    Any URL. The page’s fetch or the app’s HTTP stack asks for it, so your API, CORS and headers apply. The bundle carries the rows it was published with, so the poster and the first frame have data at once.

    data.url("https://api.example.com/sales.json", { key: "region" })

    Arrives when the chart opens

    Live

    The same source, fetched again on a schedule. Each snapshot animates in: bars slide to their new ranks, new rows grow in, missing rows leave. Try it above.

    data.url("orders.json", { key: "region", live: { every: 1.5 } })

    Arrives every every seconds · election night

    From the app

    A data slot. The chart is published once — never per user — and the app hands each user’s rows in on the device, where they stay. A sample shows until then and says which columns the rows need. Try it above.

    data.slot("spending", { key: ["month", "category"], sample })

    Arrives when the app provides it · spending

    Answered by your code

    Every request a chart makes goes past the page first. Answer it yourself — your API client with its tokens, a cache, a mock for tests, a replayed feed — and the chart never knows the difference.

    view.addEventListener("datarequest", (e) => {
  e.preventDefault();
  e.detail.respond(api.get(e.detail.url));   // bytes, text, an object, or a promise
});

    Arrives when you answer · try it

    Generated on the device

    Rows too many to send, described as expressions over the row number with seeded randomness: the same rows on every device, every time.

    data.generate(4_000_000, { x: e("randn(d.i, 1)"), y: e("randn(d.i, 2)") })

    Arrives as the chart opens · four million stars, {{size:galaxy}}

    Read by range

    Map tiles and point pyramids stay on the server as one static file each. The runtime asks for the byte ranges the view needs at its zoom — never the whole file.

    data.tiles.auto()                 // a basemap cut for your views
cloud({ data: "stars", … })       // millions of points, by the tile

    Arrives as the camera moves · maps

    In notebooks, a DataFrame is a source too: dr.bar(df, x="party", y="share") — see Python and Jupyter.
