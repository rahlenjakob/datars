Your brand

One published chart. Any brand, laid over it at runtime.

In datars a colour in a chart isn't a colour: it's an ink — $accent, $categorical[2], $card-line — resolved against the theme when each frame is drawn. Faces, text sizes, corners, strokes and the gaps between bars are tokens too. So the app that shows a chart decides its look, even for a chart published months ago by someone else. The chart below was published once and knows none of these brands.

Pick a brand: the page calls setTokens() on this one chart.

// datars over the published chart:
// nothing republished, nothing rebuilt.
const view = document.querySelector("datars-view");
view.setAttribute("mode", "light");
view.setTokens({});

What this page runs: a host app's token layer over the published chart, which knows nothing of the brand. The chart re-inks; when type or shapes change it re-lays itself out and morphs there.

Inks, resolved late

A scene stores $accent, not #4269d0. Colours bind when a frame is drawn, so a new brand or a dark mode re-inks the next frame — nothing is laid out again.

Type and shapes re-lay out

Faces, text sizes, corners, strokes and band gaps are read when a scene resolves. Change one and the engine resolves the chart again and morphs to it, like any other change: titles reflow, bars widen, points grow.

Three colours, a whole theme

The built-in theme derives its greys, gridlines, surfaces, card inks and the ink on your accent from paper, ink and accent with colour expressions — so a brand that sets those three gets a coherent chart in every mode.

Locks

Let teams restyle everything — except what's fixed

A theme can lock tokens so no later layer can change them: not the document, not the app that embeds it. This chart wears a fictional bank's house theme, which locks its brand colour, its paper and its title face. You're the host app: try to change them. The engine ignores what's locked and says so.

The host app asks for

view.setTokens({});

What the engine said

  • Nothing yet — no overrides.
export const skerry = theme({
  name: "skerry-bank",
  extends: "datars/neutral",
  tokens: {
    brand: "#1f3a5f",
    accent: "$brand",
    paper: "#f7f5ef",
    categorical: ["$brand", "#d9a441", "#3c9a78"],
    "font.title": font.file("Fraunces", "fonts/Fraunces-Bold.ttf", { weight: 700 }),
  },
  modes: { dark: { paper: "#0f1724", ink: "#e8e4da", brand: "#8fb3e0" } },
  locked: ["brand", "accent", "paper", "font.title"],
});

The layers, in order: datars/neutral → each theme that extends it → the document's own tokens → the host's setTokens(). A token locked by one layer can't be changed by any later one. The theme's own modes may still refine what it locks: the host is always free to ask for dark mode, and the bank's own dark block decides what its brand colour and paper become there. Figure source

Fonts travel with the chart

Your typeface, identical on every platform

A compiled theme's font tokens say where each face comes from — a file in your project, a URL, or a Google Fonts family. The publish step downloads it once, subsets it to the characters the chart can show and ships it in the bundle, with its licence recorded. No runtime calls a font CDN and no system font is used, so line breaks and label placement are the same in the browser, the iOS app, the Android app and the video.

  • At runtime, a font token can name a face on your server; the chart asks the page for it (a datarequest one cache can answer for every chart) and waits up to 1.5 s for it before its first frame rather than opening in a fallback.
  • Other scripts — Hebrew, Arabic, CJK — come from document fonts that join every label's fallback chain, with right-to-left ordering.
  • datars fonts doc.ts lists every font token, the face drawn, its source and its licence.

Compiled in, or laid on at runtime

Two ways in, the same tokens

Put a theme in the document and it ships with the chart: datars lint checks it, its faces are subset into the bundle, every platform plays it. Or leave the chart alone and let each app lay its own look over it — with the reader's mode.

Web

const view = document.querySelector("datars-view");
view.setAttribute("mode", "dark");
view.setTokens({ accent: "#0f766e", "radius.bar": 6 });

Or <DatarsView tokens={…} mode="dark" /> in React. Without a mode, the chart follows the reader's prefers-color-scheme.

iOS and macOS

let chart = DatarsChartView()
chart.load(.url(url))
chart.engine.setMode(.dark)
chart.engine.setTokens(["accent": "#0f766e"])

Android

val chart = DatarsView(context)
chart.load(url)
chart.setDarkMode(true)

The Android view follows light and dark today; token overrides are on the web and in DatarsKit only.

Checked

Every theme gets a specimen board and its checks

Themes declare checks — WCAG contrast of text on its background, palettes that stay distinct under simulated deuteranopia, protanopia and tritanopia, ramps that only get darker — and datars lint runs them on the resolved theme in every mode. datars theme brand.json --specimen out.png draws the standard charts, palettes and inks in all three modes side by side. Limits, plainly

What theming doesn't do yet

  • Colour changes snap in the engine. A new token layer re-inks the next frame at once; type and shape changes morph. The easing you see on this page and in the theme studio is the page's own: it hands the chart a few dozen in-between colours with setTokens(), one per frame.
  • The motion.* tokens aren't read. The built-in theme declares motion.duration, motion.easing and motion.stagger, but transitions take their timing from the document's motion rules (animation), not from the theme.
  • Android has no token overrides. The Android view switches light and dark; setTokens is on the web and in DatarsKit for iOS and macOS.
  • Generated palettes cost a search. A categorical palette generated from a colour is the costliest thing a theme resolves; a page that changes it on every input (as this one does) should pass the colours once they're made, as the theme studio does.
