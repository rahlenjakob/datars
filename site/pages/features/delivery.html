Charts are content

Publish, update and roll back charts like articles

A site or an app installs the datars runtime once. After that, charts arrive over the network as small bundles — a manifest and content-addressed chunks on any static host — and change on their own schedule: republish tonight's election map into an app that shipped in the spring, fix a typo in a chart embedded on a hundred pages, without a site deploy or an app-store review.

1

Publish

datars publish election.ts \
  --alias election --to site/

Writes site/c/election — the manifest — and site/chunks/…, named by content hash, plus any archives the chart reads by range.

2

Host anywhere static

Upload the folder to a bucket, a CDN, GitHub Pages or your own server. Chunks never change, so they cache forever; the manifest is the one small file that does. datars serve site/ tries it locally.

3

Embed once

<datars-view src="https://charts.example.com/c/election"></datars-view>

Or DatarsChart(source: .url(…)) in SwiftUI, DatarsView.load(…) on Android. Republish, and every embed follows the alias; roll back by moving it back.

Tiers

Every bundle degrades gracefully

The publish step partially evaluates the document and writes several variants, from a poster to the full source. Each runtime plays the best one it can — and every reader gets at least a picture and the text.

  1. T0Poster + accessible text. An SVG poster and the chart's text alternative. Needs nothing: email, RSS, strict CMSs, runtimes too old to play the rest.
  2. T1Playback. Baked scenes per state and the plans between them: stories, flights, scrubbing, tooltips.
  3. T2Reactive. Recipes pre-expanded; filters, brushes, sliders, linked views, live data and app data slots stay live. What the web runtime plays by default.
  4. T3Programmable. The source document, for charts whose structure depends on runtime data; needs the recipe sandbox, pinned to the author's standard library.

Nothing executable but data: T0–T2 are scenes, plans, tables, geometry and bytecode for the engine's own expression interpreter; T3 adds sandboxed script, which a page (no-script) or an app can refuse.

Data slots

One chart design, each user's data, nothing uploaded

A document can leave its data to the host: data.slot("spending", { key, types, sample }). The bundle is built once — shipped inside the app as a .datars file or fetched and cached — and the app hands in the signed-in user's rows on the device. Until they arrive, the sample shows; new rows transition the chart like any other change; rows missing the columns the chart relies on are refused with the reason.

// Web
view.data = { spending: rows };
// SwiftUI
DatarsChart(source: .url(bundled), data: ["spending": rowsJSON])
// Android
chart.loadAsset("spending.datars"); chart.provideData("spending", rowsJson)

Also in the bundle

Everything a chart needs to look the same in five years

Fonts, subset and licensed

Each face the chart draws with ships as a subset of the characters it can show, glyph ids kept so every tier shapes identically; the licence is recorded in the manifest. Text that arrives at runtime pulls per-script subsets lazily.

Shared chunks

The countries atlas, fonts and data are chunks addressed by hash: two charts on one site that use the atlas download it once, and a republish downloads only the chunks that changed.

Live data

A source can re-request on a schedule — snapshot, upsert or append — and every update animates in, without republishing the chart.

Version skew handled

A runtime whose built-in standard library differs from the author's plays the pre-expanded variant instead, so readers see what the author saw.

A single file, too

datars bundle writes the same content as one .datars file — for shipping a default chart inside an app, attaching to a message, or hosting anywhere; datars bundle inspect shows its variants and sizes.

Images on request

datars serve renders published charts to PNG, SVG or PDF by URL — social cards and previews from the same bundle.
