Charts are content

Republish a chart. Every embed updates. Readers fetch only what changed.

A site or an app installs the datars runtime once. After that, charts arrive like articles: a small manifest and content-addressed chunks on any static host, changed on their own schedule — no site deploy, no app-store review. Below, one chart embedded three times. Publish its next version and watch every embed follow, with the bytes your browser actually fetched.

A static site can't republish while you watch, so this site's build published the three versions side by side (the document), into one chunk folder, as datars publish would publish them over each other. The buttons point the three embeds at the next version, as moving the alias does; each embed then loads it as a reader returning to the page would. The chunks, their sizes and what your browser fetched are real. Rolling back is the same move, backwards: click v1.

Tiers

One bundle, four ways to play it

The publish step partially evaluates the document and writes several variants of it, from a picture to the full source. Each runtime plays the best one it can — and every reader gets at least the picture and the text. These are the variants of the chart above, as published.

Every variant of v3, to scale

{{variants:delivery-v3}}

Nothing executable but data: T0–T2 are scenes, plans, tables, geometry and bytecode for the engine's own expression interpreter; T3 adds the source document, run in the recipe sandbox, which a page (no-script) or an app can refuse. A runtime whose built-in standard library differs from the author's plays T2, so readers see what the author saw.

Trust

Signed manifests: the runtimes check, the CLI doesn't sign yet

A manifest can carry an ed25519 signature, and every runtime can be told whose charts to play: <datars-view publishers="ed25519:…">. A chart that isn't signed by one of them doesn't play. That's the checking half, and it works today — the chart beside this text is the one above, unsigned, embedded with a key it can't match.

The signing half isn't exposed yet: datars publish doesn't sign bundles, so leave publishers unset for charts you publish with the CLI. It's on the list in the status page.

Data slots

One chart design, each user's data, nothing uploaded

A document can leave its data to the host: data.slot("spending", { key, types, sample }). The bundle is built once — shipped inside the app as a .datars file or fetched and cached — and the app hands in the signed-in user's rows on the device. Until they arrive, the sample shows; new rows transition the chart like any other change; rows missing the columns the chart relies on are refused with the reason.

// Web
view.data = { spending: rows };
// SwiftUI
DatarsChart(source: .url(bundled), data: ["spending": rowsJSON])
// Android
chart.loadAsset("spending.datars"); chart.provideData("spending", rowsJson)

Also in the bundle

Everything a chart needs to look the same in five years

Fonts, subset and licensed

Each face the chart draws with ships as a subset of the characters it can show, glyph ids kept so every tier shapes identically; the licence is recorded in the manifest. Text that arrives at runtime pulls per-script subsets lazily.

Shared chunks

The countries atlas, fonts and data are chunks addressed by hash: two charts on one site that use the atlas download it once, and a republish downloads only the chunks that changed.

Live data

A source can re-request on a schedule — snapshot, upsert or append — and every update animates in, without republishing the chart.

Version skew handled

A runtime whose built-in standard library differs from the author's plays the pre-expanded variant instead, so readers see what the author saw.

A single file, too

datars bundle writes the same content as one .datars file — for shipping a default chart inside an app, attaching to a message, or hosting anywhere; datars bundle inspect shows its variants and sizes.

Images on request

datars serve renders published charts to PNG, SVG or PDF by URL — social cards and previews from the same bundle.
