A chart a screen reader can read, not a picture it can't

Every mark in datars carries semantics — a role, a label, a value, a reading order — and the standard recipes fill them in: “Moderates: 68 seats”, not “rect”. Each platform's runtime hands them to its assistive technology. Below is one chart, and what each kind of reader gets from it: the list a screen reader walks, the buttons a keyboard reaches, the colours as other eyes see them, high contrast, and less motion.

    Contrast

    Text and rules go full strength; the colours that come from the document's keys stay theirs. The page or app turns it on — the web element doesn't follow the system's prefers-contrast by itself yet.

    Your device asks for reduced motion: the chart already plays it. Untick to see the full motion.

    With reduced motion every change is a short crossfade instead of bars growing and receding, and autoplay and clocks stay still. It's the reader's system setting by default — prefers-reduced-motion, iOS Reduce Motion, Android's Remove animations — and a page can decide per chart:

    On every platform

    The native way, everywhere

    • Web

      A hidden list kept in step with the chart, in reading order: every labelled mark as text, clickable marks as buttons, engine-drawn sliders as native range inputs and dropdowns as native selects, real links over linked text; a polite live region that announces each step's narration. A keyboard's place in the list is outlined on the chart.

    • iOS and macOS

      VoiceOver elements with per-item frames, so explore-by-touch finds each bar where it is drawn; activatable marks; engine-drawn sliders as adjustable elements; macOS accessibility children.

    • Android

      TalkBack reads the chart through an accessibility node provider: virtual nodes with screen bounds, clickable marks, adjustable sliders. The node tree has been checked on the emulator; it hasn't yet been driven by TalkBack itself.

    • Desktop

      The same tree through AccessKit, for VoiceOver, Narrator/NVDA and Orca, with interactive marks as buttons and sliders adjustable — unit-tested, not yet exercised with a real screen reader.

    • Video

      WebVTT captions generated from the story's narration, alongside every MP4 datars video renders.

    • SVG and PDF

      SVG exports and posters carry titles, descriptions and roles; PDF keeps text as searchable text.

    For every reader

    Beyond screen readers

    Intents, not mouse events

    Documents bind inspect and activate, not hover and click: activate is a click, a tap, Enter on the mark's button, or a double-tap with VoiceOver or TalkBack. Every input, intent by intent →

    Touch that doesn't trap

    On a phone a finger that lands on a brush, a pannable map or a slider drags it; anywhere else it scrolls the page, so a chart the width of the screen never holds the reader.

    Reduced motion, per chart

    The system setting by default; reduced-motion="reduce" or "no-preference" when the page knows better — an opt-in “show me the motion” button, a side-by-side comparison.

    Colour you can tell apart

    Themes are checked for WCAG contrast of text on its background, and generated palettes for colours that stay distinct under simulated protanopia, deuteranopia and tritanopia. The theme studio shows the checks →

    Text that is text

    Titles, labels and annotations lie over the canvas as real text: selectable, findable with Ctrl+F, enlarged with the page.

    Data, not just a picture

    Every published bundle carries an SVG poster with titles and roles, and its accessible text — the chart is understandable before the runtime loads, and where it never does.

    Caught before publishing

    The linter knows what makes a chart inaccessible

    datars lint checks identity, encoding, legibility, accessibility and the theme: interactive marks without an accessible label, labels that collide or are cut off at the edge, more categorical colours than readers can tell apart, text colours that fail the theme's WCAG contrast checks, palettes that collapse under colour-vision deficiencies, rows without keys, and maps without the credit their data's licence requires. Agents get the same findings over MCP.

    Plainly

    What isn't there yet

    • Brushes and pannable views have no keyboard path of their own. Give the same signal a control (a std range or slider, which keyboards reach as native inputs), or set it from the page.
    • The live region speaks a step's narration, not the result of a click. The button says it instead: its label follows the state (Moderates: 68 seats, in the coalition), and the coalition's total is a labelled item in the list.
    • No tooltip on keyboard focus. A focused button reads the same label a tooltip would show, and the mark is outlined; the drawn tooltip is for the pointer.
    • High contrast is the page's choice. The web element doesn't pick it from prefers-contrast or forced colours by itself yet.
    • Long lists stop at 500 marks on the web — a map of thousands of counties is in the text description, not read out mark by mark.
    • Android and desktop trees are tested, but not yet with TalkBack, NVDA or Orca driving them.
