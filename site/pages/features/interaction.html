Interactive

Hover, click, brush, drag, zoom — and not one event handler

In datars an interaction is a line in the document. A mark binds an intent — inspect, activate, brush, drag, pan, zoom — to an action that writes a signal; every table and mark that reads the signal follows, with a keyed transition. Views link because signals are global. The lab below is one document with four of those lines. Use it, watch the signals change on the right, and switch the lines off.

    A finger is the chart's where the chart drags

    A touch that lands on a brush, a pannable view or a slider stays with the chart; a touch anywhere else scrolls the page, so a chart as wide as the phone never traps the reader. Two fingers over an explorable view zoom it.

    The keyboard reaches what you can click

    Each chart keeps a hidden list in step with what it draws: clickable marks as buttons, engine-drawn sliders as native range inputs. In the lab, Tab past the chart into the bikes' buttons and the time limit's slider. Accessibility →

    Brushes and cameras need a second way in

    A brush or a pan has no keyboard equivalent of its own yet. Give the same signal a control — a std range or slider — or set it from the page, as the lab's buttons do: the chart can't tell the difference.

    Each one a line

    Scrubbers, drill-downs, overview and detail, controls

    Four more documents, each built around one binding. Nothing on this page handles their events.

    Drag across the day

    Scrub a chart with a chart

    The day's curve is the scrubber: a shape over the plot's area turns a drag into hour through the plot's own x scale, snapped to whole hours, and the stations re-rank — each bar keyed by its station, so it slides to its new place. A keyboard gets the same as a native slider.

    plot({ data: "day", x: "hour", y: "trips", children: [
  area(), line(), rule({ axis: "x", value: e("hour") }),
  shape(plotArea, { on: { drag: scrub("hour", { step: 1, min: 0, max: 23 }) } }),
] }),
// the ranking reads it
now: { from: "trips", ops: [op.filter(e("d.hour == hour")), op.sort(["trips", "desc"])] },

    Try every control

    Controls the engine draws

    Sliders, ranges, segmented choices, dropdowns, switches, checkboxes and buttons are std recipes: drawn by the engine, identical on the web, in apps and in a video, as quick as a UI — and offered to keyboards and screen readers as native controls. On a phone a dropdown opens the phone's own picker.

    The vocabulary

    Signals, intents and actions

    Everything interactive on this site is built from these — declared in the document, so it travels with the chart to every platform.

    Signals

    signal.num, str, bool, key, keyset, range — and clock, which counts up while a settled scene reads it. Story steps set them; marks, tables and cameras read them. Built in: inspected, a brush's .lo/.hi/.active, a view's .x/.y/.zoom.

    Intents

    inspect, activate, brush, drag, pan, zoom and pick. Documents bind intents, not mouse events, so the same chart works with every input the host has.

    Actions

    Set a signal, toggle a key in a set, brush a range, scrub a value along a scale, send the program an event, or enter a drill-down chapter with the clicked key — all data, no callbacks.

    Tooltips

    Every data mark has a label — “E-bike, 12 October: 4.6 km in 17 min” — shown on inspect, drawn by the engine so it's the same on every platform, and read by screen readers.

    Explorable views

    A view's camera can name signals that drag, the wheel and a pinch move, between a minimum and a maximum zoom. The four-million-star galaxy is one; a story step flies the camera back into the narrative.

    Hover states

    hover() is true while the pointer is over the element: a control's wash, a halo round a thumb, a label lighting up — animated, never on a touch screen, and costing a new scene only for the elements that ask.

    Talk to the page or the app

    Host and chart, both ways

    The page or app can drive the chart — set a signal from its own filter, jump to a state, hand in data — and follow it: signal says what the reader changed, pick which row a click landed on, state which step the story is on. The lab's right-hand panel is built from exactly these.

    • Web: setSignal(name, value), signals, send("goto:ranked"), data = { slot: rows }, and the signal, pick and state events.
    • iOS: DatarsChart(source:state:) follows SwiftUI state; the engine's setSignal sets numeric signals.
    • Android: send("next"), goTo(index), provideData(…).

    const chart = document.querySelector("datars-view");

// The page drives the chart…
weekPicker.addEventListener("change", () =>
  chart.setSignal("days", { lo: weekPicker.from, hi: weekPicker.to }));

// …and follows it.
chart.addEventListener("signal", (e) => {
  if (e.detail.changed.includes("kinds")) showBikes(e.detail.signals.kinds);
});
chart.addEventListener("pick", (e) => showTrip(e.detail.row));

    Text

    Chart text you can select, copy and find

    A chart's titles, labels and annotations are drawn by the engine, and on the web they're also laid out as real text over the canvas, glyph for glyph: drag to select a title and copy it, find a label with Ctrl+F, and search engines read it. A drag that starts on a label inside a brush or a pannable view is the chart's drag, not a selection.
